# PuREPower Dealer Lead Router

A complete web application for PURE Energy's PuREPower business that captures customer leads from multiple sources (website, AI voice calls, WhatsApp, dealer walk-ins), automatically assigns them to the correct regional dealer based on pincode, and provides an admin dashboard for tracking and managing leads.

---

## Features

- **Lead submission form** with real-time dealer preview as the customer types their pincode
- **Automatic dealer assignment** using pincode-prefix matching against the authorised dealer list
- **Duplicate prevention** via Firestore transaction using the mobile number as the document ID
- **Admin dashboard** protected by Firebase Authentication with real-time Firestore subscription
- **Status management** — change a lead's status (New → Contacted → Converted → Lost) from the dashboard
- **Filters and search** — filter by dealer, status, or free-text search
- **Legacy CSV import** — Python script that cleans `legacy_leads.csv`, generates a reconciliation report, and imports valid records into Firestore
- **36 automated tests** covering all validation rules, dealer assignment, and reconciliation logic
- **Fully responsive** dark-mode UI built with HTML + CSS + Vanilla JS (no framework required)

## Authentication Setup

### Step 1 — Create an admin user in Firebase Console

1. Firebase Console → Authentication → Users → Add user
2. Enter an email (e.g. `admin@pureenergy.in`) and a strong password
3. Note the **UID** shown in the users list

### Step 2 — Set the admin custom claim

The Firestore rules require `request.auth.token.role == 'admin'`. This claim must be set server-side.

Create a file `scripts/set_admin_claim.js` (do NOT commit it):

```js
const admin = require("firebase-admin");
const serviceAccount = require("./serviceAccountKey.json");

admin.initializeApp({ credential: admin.credential.cert(serviceAccount) });

const uid = "PASTE-THE-UID-HERE";
admin.auth().setCustomUserClaims(uid, { role: "admin" })
  .then(() => { console.log("Admin claim set for", uid); process.exit(0); })
  .catch(console.error);
```

Run it once:

```powershell
node scripts/set_admin_claim.js
```

After setting the claim, **the user must sign out and sign back in** for the new token to take effect.

> Without the admin claim, the user can sign in but Firestore Security Rules will deny all read/write operations on the leads collection.

## Firestore Schema

**Collection:** `leads`
**Document ID:** normalized 10-digit mobile number (for form submissions) or `lead_id` (for CSV imports)

| Field | Type | Notes |
|---|---|---|
| `leadId` | string | Document ID / original CSV lead_id |
| `name` | string | Trimmed customer name |
| `mobile` | string | 10-digit normalized mobile |
| `pincode` | string | 6-digit string |
| `product` | string | Selected product name |
| `source` | string | One of the 5 allowed sources |
| `dealer` | string | Assigned dealer name or "In-house Sales" |
| `status` | string | New / Contacted / Converted / Lost |
| `createdOn` | Timestamp | Server-generated (or CSV date for imports) |
| `updatedOn` | Timestamp | Updated on every status change |

## Security Assumptions

- The Firestore rules deny all access by default.
- Only users with the `role: 'admin'` custom claim can read leads or update status.
- Lead creation from the form requires the user to be signed in.
- The mobile number as document ID enforces uniqueness at the database level.
- No customer data is readable without authentication.
- The Firebase Admin SDK (used in Python import) bypasses rules — it validates data itself before writing.

---

## Dealer Assignment Rules

1. Pincodes are treated as strings, never as numbers.
2. The first 3 characters of the pincode form the "prefix".
3. Each dealer has one or more prefixes separated by `|` in `dealers.csv`.
4. Whitespace around prefixes is trimmed before comparison.
5. If multiple dealers share a prefix (overlap), the dealer that appears **first** in the list wins (deterministic).
6. If no dealer matches, the lead is assigned to **"In-house Sales"**.
7. The frontend (`dealers.js`) and the Python script (`clean_leads.py`) use the same matching logic and produce identical results for the same input.

## Troubleshoot Common Errors

| Error | Cause | Fix |
|---|---|---|
| `Permission denied` in Firestore | User is not signed in or missing `role: admin` claim | Sign in and set the admin custom claim |
| `firebaseConfig` not replaced | Placeholder values still in `firebase.js` | Copy real config from Firebase Console |
| `auth/invalid-credential` | Wrong email or password | Check credentials in Firebase Auth users list |
| `ENOENT serviceAccountKey.json` | Wrong path to credentials | Check `GOOGLE_APPLICATION_CREDENTIALS` path |
| `firebase: command not found` | Firebase CLI not installed | `npm install -g firebase-tools` |
| Dashboard shows no leads | No data in Firestore | Run the CSV import or submit a test lead |
| Mobile already exists error | Duplicate submission | Each mobile number maps to exactly one lead |

## Assumptions and Trade-offs

1. **Mobile as document ID**: The 10-digit mobile number is used as the Firestore document ID for form submissions. This enforces uniqueness at the database level without Cloud Functions. Trade-off: changing a mobile number requires migrating the document.

2. **Admin claim required**: The Firestore rules require `role: 'admin'` as a custom claim. Without it, even authenticated users cannot read leads. This is the correct security posture but requires one-time provisioning.

3. **No Cloud Functions**: The app stays within the Spark (free) plan. Duplicate prevention is achieved via Firestore transactions. Trade-off: concurrent submissions by the same user in two browser tabs could theoretically race, but Firestore transactions serialise access to the same document, so only one wins.

4. **Dealer list is embedded in JavaScript**: The dealer list is hardcoded in `dealers.js` from `dealers.csv`. If the dealer list changes, the JS file must be updated and redeployed. For dynamic management, move the list to a Firestore `dealers` collection.

5. **Import uses original `lead_id` as document ID**: CSV imports use `L1001`, `L1002`, etc. as document IDs. Form submissions use the mobile number. These two spaces are separate but both live in the same `leads` collection.
